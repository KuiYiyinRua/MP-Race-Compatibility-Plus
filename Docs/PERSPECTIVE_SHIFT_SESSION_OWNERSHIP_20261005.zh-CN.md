# Perspective Shift 联机主角认定生命周期修复

目标模组：`ferny.PerspectiveShift`，创意工坊 `3686618980`。本次修改的是本项目的兼容层，不修改目标模组的文件。

已于 2026-10-05 本地部署 **3.0.148**。正式主 DLL 与通过测试的候选 SHA-256 完全一致，正式程序集目录中没有本次测试组件；部署回执为证据根目录的 `deployed.json`。

## 行为

- 读取存档重新主持联机房间时，在首份共享快照生成前释放所有旧主角认定，包括长期离线玩家的认定。房主与其他玩家都需要主动重新选择主角。
- 同名玩家退出并重新加入仍在运行的房间时，仅同步释放该玩家上一次连接的认定；保留房主和其他玩家的认定。普通加入点保存、同步和地图切换不清空整个房间的认定。
- 单机载入带有旧联机认定的存档，也会解除旧联机占用。取消原先将单机主角自动迁移为房主主角的行为。
- 认定同时记录玩家名、当前连接 ID 和递增认定序号。旧认定的移动、点击与开火输入不能恢复控制或作用于新认定。
- 释放时停止兼容层自己的移动任务、取消待执行开火、清理本地按键/预测/镜头状态，并解除征召。原有 Lord 仍存在且角色适合恢复时，只恢复一次。
- Authentic 模式清理旧主角 ID 后，健康的玩家角色仍有明确的“接管控制”入口；不需要保留错误的旧主角 ID 才能重新认定。

## 根因与额外修复

原兼容层把玩家名与角色的绑定保存在存档中，载入后可以自动恢复本地主角，而玩家名不足以区分旧房间、旧连接与本次主动认定。`R01-Baseline` 中旧版 DLL 在重新开房后仍保留 `LongOffline` 和 `PsClient` 的认定，复现了此问题。

征召回归还发现目标模组的 `State.IsAvatar` 使用 `AggressiveInlining`：只补丁这个辅助函数，已经编译的原调用方仍可能使用本地单例。`R04-Smoke` 的真实双端轨迹在同一征召命令中分别进入 `JobGiver_MoveToStandable` 与 `JobGiver_Orders`。当前版本替换目标程序集内实际调用该函数的 48 个方法调用点，统一通过共享认定表判断；单机路径仍保留原单例语义。此项修复没有通过删除征召回归、忽略 desync 或包裹整张地图随机数来规避。

认定列表的排序结果改为仅在表发生变化时重建；按角色和玩家查找改用直接循环，移除常用查询中的 LINQ 闭包分配。没有对总体帧率作量化承诺。

`R07` 的两图压力测试还发现，切换镜头后原移动心跳把本地 `CurrentMap` 与角色自身地图同时放进同步上下文，触发 `SyncMethod map mismatch`，指令被拒绝但不一定立即失步。当前版本的所有带 Pawn 参数的动作由 Pawn 序列化决定地图；查看其他地图或世界视图时发送停止输入，并阻止屏外主角接收鼠标点击/开火。测试控制器新增这类异常的失败门槛与跨图停止输入回执检查。

## 同步与状态边界

| 路径 | 执行边界 | 共享状态/副作用 |
| --- | --- | --- |
| 新房间 | `HostUtil.CreateSession` 标记，首次 `SaveLoad.SaveGameData` 前清理 | 清空旧认定，保留认定序号上限；清理结果进入初始共享快照 |
| 主动认定 | 原生 Gizmo → `SyncClaimAvatarWithMode` | 从实际同步命令取得玩家身份与连接 ID，独占认定，准备任务，暂存 Lord |
| 退出后重连 | 本地检测连接 ID 变化 → `SyncReleaseAvatarForPawn` | 序列化 Pawn 决定地图，按玩家、Pawn、旧序号精确释放 |
| 主动释放/取消征召/健康回调 | 同步命令或确定性游戏回调 | 先移除认定，再调用任务、征召与 Lord 回调，避免递归释放 |
| 移动/点击/开火输入 | 同步命令 | 校验玩家名、连接 ID、Pawn、认定序号；拒绝过期输入 |
| 已接受的延迟开火 | Pawn 所在地图的共享 tick | 使用已同步的认定状态执行；不使用各端本地连接 ID 再判断 |
| 拒绝提示 | 本地 UI 通知队列 | 不在仅发起端的同步命令执行中分配共享 Message ID |
| 本地视角恢复 | 玩家名与连接 ID 都匹配 | 仅恢复当前连接已主动认定的角色，不从玩家名猜测控制权 |

专项负载含目标模组及必要依赖，共 14 个包。覆盖原生认定按钮、征召、释放、跨图重新认定、旧输入拒绝、拒绝抢占他人角色、Lord 恢复与共享快照保存。每轮完成前要求主客地图/world tick、随机状态及认定表完全一致。

冷重连阶段的独立核对见 `Audit/rejoin-milestones.json`：普通/异步模式各 3 次，第三次重连后均超过 10,000 个共享 world tick。初始认定等待条件修正后，单独重跑长测的结束与保存阶段；游戏候选 DLL 保持相同哈希。异步阶段启动时两图均设为 Superfast，并仅在客户端切换镜头；不宣称覆盖全部手动调速组合。

夹具在保存后仅接受这种空角色引用：同一测试进程此前已记录该角色死亡/销毁，且当前共享认定表没有其归属。未确认死亡的空引用、存活角色丢失归属或已死亡角色恢复归属仍为失败。

完整通过的最终证据汇总见 `Audit/final-verification.json`。R09、R10、R15、R16 的主客最终快照一致，未发现本次功能的失步、同步方法异常或断言失败；R15/R16 均在角色自然死亡后核验两端同步清除了认定，房主的存活角色认定保留。

未提供此问题对应的用户原始故障存档，因此不把专项测试等同于整个模组合集、所有角色技能或所有操控组合的全面验证。既有其他兼容模块的验证范围没有因此扩大。

加载日志中存在原环境已有的 `ReflectionOnly` 解析 `UnityEngine.InputLegacyModule` 的诊断，修复前 `R01` 也有同样记录；之后游戏完成载入并执行本次操作测试。本次没有将它写成“所有日志无异常”，也没有修改程序集依赖加载器。

## 使用与回退

所有联机玩家需要安装相同版本并完全退出后重启 RimWorld。房主重新主持旧存档后，让每位玩家重新认定主角。

修复前主 DLL、PDB、`About.xml` 与版本/哈希清单保存在证据根目录的 `Before`。如需回退，应停止游戏后成套恢复上述旧文件，并让所有玩家使用一致版本；不要在游戏进程运行中替换 DLL。本次未向创意工坊发布。
