# Desync 442 和 443 原因分析与补丁决策

结论：442 的直接分歧是客户端单独生成世界地点；原版地点生成器使用进程对象哈希安排检查时间，是已核实且与轨迹吻合的确定性缺陷，建议针对该时间门槛做窄补丁。443 是重连后的搬运执行分歧，主机多了一次拆分物品与分配 ThingID 的调用，尚不足以确定导致分歧的输入或状态，暂不对搬运、近战动画或全局随机数打补丁。

本次只做离线分析和证据归档，没有修改或部署产品补丁，没有启动游戏，也没有验证补丁效果。

## Desync 442：世界地点生成的触发时间不确定

最后有效网络 tick 为 `13591`，报告失步 tick 为 `13650`，间隔 59。最早可见分歧为 trace `80`、网络 tick `13640`。

主机此处继续地图内的 `AM.Processing.MapPawnProcessor.CompileListOfAttackers → Rand.MTBEventOccurs`。客户端则在世界 tick `24458` 进入：

```text
WorldComponent_LocationGenerator.WorldComponentTick
  → GenerateUntilTarget(PlanetLayer)
  → GenerateLocationForLayer
  → TryFindSiteTile / TileFinder
  → 随机选地点、地点类型、名称与资源
  → WorldObjectMaker.MakeWorldObject / GetNextWorldObjectID
```

分歧前的可见 context trace `40–79`，两端 tick、哈希、附加状态和堆栈一致。主机完整 trace count 为 132，客户端为 204。在提供的 context 窗口中，客户端有 40 条地点生成相关记录、至少 7 条新 WorldObject ID 分配；主机相应窗口为 0。窗口之外的地点数量不可从本包准确还原。

最终错误是 `Wrong random state for the world`。地图随机检查先于世界随机检查，因此此错误说明该次检查的地图随机序列通过，世界随机序列未通过。近战动画出现在主机对应位置是因为客户端插入了额外世界调用；这不是近战动画自身失步的证据。

### 已核实的代码缺陷

与包内游戏 MVID 完全一致的本机 H 盘 `Assembly-CSharp.dll`，在 `WorldComponent_LocationGenerator.WorldComponentTick` 中执行：

```csharp
if (GenTicks.IsTickInterval(planetLayer.GetHashCode().HashOffset(), 90000))
{
    // 地点数量不足时 GenerateUntilTarget(layer)
}
```

`PlanetLayer` 是引用类型，继承自 object，未覆盖 GetHashCode；该对象哈希随进程实例而变化，不是保存/联机快照中的稳定层标识。主机、客户端或冷重连构造出的层对象可能在不同世界 tick 命中 90000 tick 的检查。地点不足时，单端生成真实世界对象并消费世界 Rand，直接形成本包的差异。

包内 Harmony 清单没有对 WorldComponent_LocationGenerator 该门槛的修复；当前本机兼容源和 Multiplayer 源也未找到此修复。Multiplayer 已对 FishShadowComponent 的类似对象哈希门槛做过定点替换，但没有覆盖此处。

证据强度：**客户端单独进入地点生成及世界 Rand 分歧已证实；对象哈希时间门槛是已核实的代码缺陷，对 442 的归因有强支持。** 原包没有记录两端 PlanetLayer 对象哈希、检查前地点总数和构造时 worldLocationsTarget，不能宣称这些现场值已被实测。

### 补丁决策

建议修复，仅在多人模式下将此方法中的对象哈希替换为基于保存稳定 `PlanetLayer.LayerID` 的调度标识，保留原 90000 tick 间隔、地点不足判断、随机生成和世界对象保存逻辑。不要全局替换 object.GetHashCode，也不要通过隔离地点生成 Rand、跳过地点生成或忽略同步检查来掩盖真实单端生成。

验收需先用两端诊断记录证明同层在相同世界 tick 命中门槛，再比较生成地点的 tile/def/ID/资源及世界 Rand。覆盖两图异步时间和三次冷重连；必须自然推进穿过检查门槛，短于该门槛且未触发生成的稳定运行不算修复证明。

## Desync 443：机体搬运时多了一次新物品分配

443 在 442 后重新加入。最后有效网络 tick 为 `19501`，报告失步 tick 为 `19562`，间隔 61。最早可见分歧为 trace `78`、网络 tick `19541`、地图 tick `26405`。

主机由 `Nivarian_MechUnit12893` 执行以下调用：

```text
Pawn_PathFollower.PatherArrived
  → JobDriver.Notify_PatherArrived / ReadyForNextToil
  → Toils_Haul.StartCarryThing 的 initAction
  → Pawn_CarryTracker.TryStartCarry
  → ThingWithComps.SplitOff / Thing.SplitOff
  → ThingMaker.MakeThing
  → Thing.PostMake / ThingIDMaker.GiveIDTo
  → UniqueIDsManager.GetNextThingID
```

客户端对应位置直接进入该图正常的近战动画概率检查，没有这条新物品 ID 分配记录。主机完整 trace count 为 228，客户端为 227。将主机 trace `79–117` 对齐客户端 `78–116`，后续 **39/39** 条 tick、哈希、附加状态和完整堆栈逐条相同。这是具体的一条分配记录差异，不是“双方随机数一直不同”。

最终错误为 `Trace hashes don't match`。安装版 Multiplayer 的 CheckForDesync 顺序为地图 Rand、世界 Rand、命令 Rand、trace 哈希。因此该次检查的三个 Rand 比较均通过，随后轨迹比较失败。Rand 相同不代表物品、任务和 ID 状态全部相同，不能将这包直接判成误报。

### 能确定与不能确定的范围

原版 `Thing.SplitOff` 在 `count >= stackCount` 时直接搬走原物品；只有拆走部分堆叠时才调用 MakeThing 并分配新 ID。`TryStartCarry` 的数量受任务数量、源堆叠数量和 AvailableStackSpace 限制。因此本包要求继续比较两端该机体的任务/Toil/位置、源物品与堆叠数量、实际取走数量和搬运容量。

原包只有日志、轨迹、JIT 和元数据，没有这几个状态的双端快照。它不能单独证明是取走数量不同、源物品数量不同、任务进度不同，或某个调用进入了额外 Rand/trace 作用域。

JIT 的辅助线索：主机在网络 tick `19488` 首次编译控制中心模块安装等待路径，两端在 `19495` 都到达容器 PopOutThings/ThingOwner.TryDropAll；主机还在 `19522` 首次编译 ContainerCompHasAllIngredients。下一步应优先围绕控制中心模块安装及其供料/搬运链采样。**JIT 记录仅表示首次编译，不能证明客户端没有执行、某个 UI 未同步，或缺少序列化。**

安装版控制中心已经序列化模块安装请求、队列、进度和状态；通用容器也已经序列化 ingredientsContainer 与 requiredIngredients。不能仅凭“重连后失步”添加一套猜测性的队列保存。

包内 Thing.SplitOff 的母舰补丁 FleetMaterialSplit 仅在前缀记录临时物品所属批次、后缀跟踪返回物品，未直接跳过原方法或更改 split count。它不是已被证明的原因。

证据强度：**首处分配调用分歧已证实；导致该分歧的具体状态来源尚未定位。**

### 补丁决策

暂不修改原版搬运、近战动画、全局 ThingID 或关闭 trace 比较。最小下一步是在真实动作前后使用只读、受开关控制的观察记录：pawn ID/map tick/job def/count/target/toil、源 ThingID/def/stackCount、carry 容器、AvailableStackSpace、SplitOff 参数/返回 ID、控制中心请求/需求/库存、ID 分配与 Rand scope 深度。用原始联机保存/重放、两图异步时间、冷重连和同一模块操作复现后，选择实际失去同步或重连恢复错误的窄边界。

## 其他可见错误

两包加载中均有 RaceTrioCompatibility 和 TaleNivarianCompatibility 的 NivarianAidSettings 构造空引用，以及 UnityEngine.InputLegacyModule 的 ReflectionOnly 依赖错误。它们是需要单独核查的启动/加载问题，当前没有证据连接到上述两个首次分歧；不将它们当作本次失步根因，也不凭日志距离自动修补。

443 同会话另有 217 行重复 `Event.Use() ... repaint`。原日志完整保留，阅读副本只折叠重复 UI 警告和堆栈行；两包最终会话分别读完 96 和 92 条其余记录，没有用旧会话末行归因。
