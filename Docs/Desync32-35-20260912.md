## 结论与置信度

**已由轨迹证明：33、34、35 都是在主机单独执行 `Caravan_NeedsTracker.TrySatisfyJoyNeed → TryRandomElementByWeight` 时首次产生分歧。** 这三个上下文窗口各有 40 条完全一致的前序记录。33 的后续世界 Rand 计数因此相差一次；34、35 随后地图上的 Cumpilation 与近战动画记录仍能逐条对齐。不能因为客户端首条显示 Cumpilation、Vanilla Social Interactions 或 AM 就把它们认定为本次根因。

- 33：最后有效共享 tick 1809391；首分歧 trace 653 / tick 1809429，世界 tick 818439，间隔 38。
- 34：最后有效共享 tick 1812061；首分歧 trace 521 / tick 1812098，世界 tick 819492，间隔 37。
- 35：最后有效共享 tick 1814311；首分歧 trace 730 / tick 1814351，世界 tick 820742，间隔 40。
- 32：最后有效 tick 1694300；日志在 1695060 报命令随机状态不一致，间隔 760。host/local 均无调用轨迹（trace count 0 / -1），无法定位具体命令和执行方法。

**已由安装源码链和回归测试证明的兼容缺陷：** Almost There Fork 的 `Caravan_NightResting_Patch.Postfix` 在默认“快到了”模式下用 `EstimatedTicksToArrive(caravan, true)` 的静态缓存决定是否夜休。缓存不保存、不参与同步，也可被本地界面填写；有效性仅判断 `TicksGame - cacheTicks < 100`，没有下界。异步地图时钟较大时写入的缓存，在较小的世界时钟中会被长期视为有效。夜休判定进一步影响 `Caravan.CantMove → Caravan_PathFollower.MovingNow → GetCurrentJoyGainPerTick`，可直接让一端跳过娱乐恢复及世界 Rand 抽取。

**对 33–35 的归因属于强支持，尚非同存档复现闭环。** 用户确认当时有开启“快到了”模式的远行队；33 的主机 JIT 在共享 tick 1809267 编译了来自该夜休回调的 ETA 查询。JIT 只证明执行路径到达，不能证明缓存数值。ZIP 没有远行队具体 ID、缓存值、路径或娱乐资格快照，不能排除其他上游状态差异。

本机另找到 `MpReplays/Player9689's game.zip`，共享 tick 1814922、318 项加载表，已冻结为 `RepresentativeReplay.zip`。其中有远行队 1357（默认模式 0）及 Kiiro_Race99662、50118、99671 三名成员；这支持场景核对，但它是 35 号之后的快照，不是分歧前双方完整状态。

## 32 号的独立限制

32 的日志显示配置同步明确要求重启：核心补丁为启动时生效配置，另有客户端独有 BetterInfoCard、RJWHookupSettingsController 配置；之后使用了 `Connecting anyway ... Configs match: False`。这是已知无效配置基线，可能影响命令重放，但没有命令轨迹，不能把配置差异认定为唯一原因，也不能宣称 ETA 补丁修复了 32。

33–35 的 `local_logs.txt` 三份逐字相同，且被截为 10,000 行，里面唯一明确的 `Desynced after` 仍是 32 的旧事件。分析后三包使用各自 `desync_info` 和轨迹，没有把旧日志 tick 当作新故障时刻。最终日志段还有重复空引用、YaOpt 索引重复、销毁对象保存警告；没有证据将其与首次娱乐分歧直接等同。
