# 最新联机存档性能诊断（2026-09-24，验证中）

本次以用户最新联机存档的冻结副本，在完整原模组顺序下单机主持 Multiplayer，使用 Dubs Performance Analyzer 测量。原存档、原配置和正式发布程序集均未覆盖。

## 已确认的主要热点

渡鸦族防御中枢的 `Patch_DefenseHub_UniversalTurret.Postfix_TryStartShootSomething` 在每次进入有效中枢分支时，都重新调用 `AccessTools.FieldRefAccess<Building_TurretGun, int>("burstWarmupTicksLeft")` 创建字段访问委托。炮塔即使没有找到敌人，也可能不断走到这条路径。

最新存档包含 99 座炮塔。在相同 1,800 个世界 tick 窗口中，该委托工厂被调用 11,520 次；第一次控制测量中，它占用约 14.82 秒，而炮塔目标搜索只占约 0.25 秒。输送网络的细分测量约 0.36 秒，当前不应优先改动它。

候选程序集 `Meow.LatestSavePerformance.dll` 只缓存这个字段的访问委托，不缓存字段值、目标、炮塔对象、随机结果，也不改变炮塔更新频率或开火判断。原 Raven 方法继续执行原分支、字段读取和写入。目标 IL 不符合预期时拒绝安装，并记录 `REQUIRED_TARGET_FAILED`。

## 已完成的测量

- 原设置（异步时间和失步追踪开启）：两次约 28.04、28.19 world TPS。
- 仅关闭失步追踪、使用相同粗粒度计时目标：31.70 world TPS；与相邻控制相比约提高 12.5%。此设置收益不能直接与后续不同采样目标相加。
- 细分炮塔方法的交替 A/B：原工厂 28.95 → 缓存 46.58 world TPS；再次原工厂 31.12 → 缓存 42.84 world TPS。两轮均有明显收益，波动仍存在。
- 对应 Raven postfix 总耗时第一轮从约 14,841 ms 降至 7.65 ms，第二轮从约 14,592 ms 降至 8.09 ms。
- 四段均从同一冻结存档开始、完成 1,800 world ticks；每段恰好 11,520 次访问，控制和候选各自只走指定实现。
- 四段的起止世界／地图 tick 和 Rand 状态一致；99 座炮塔的 ID、定义、HP、预热、冷却和目标记录一致。

所有 TPS 均为世界 tick/秒。异步模式下世界、地图和网络共享时钟不同，不能混用。DPA 方法的 inclusive 时间存在嵌套，不能相加当作总成本。

无方法采样的六段测试也已完成，每段均确认 `TIMING_ONLY` 和 `profilers=0`：

- 失步追踪关闭，两轮原工厂／缓存分别为 32.97／50.06 和 34.09／47.97 world TPS，分别约提高 52% 和 41%。
- 保留原失步追踪设置：32.30／45.73 world TPS，约提高 42%。这是当前最接近日常原设置的同条件对照。
- 六段的世界／两地图 tick、Rand、99 座炮塔记录状态及访问次数均一致，输入哈希未改变。
- 本轮原工厂在 trace 开关间的差距比此前粗粒度采样更小，因此不能把“关闭追踪提高 12.5%”当作稳定承诺。炮塔缓存补丁本身在两种追踪设置下均有收益。

上述证据证明单机主持中的热点和收益，尚不代表双端长时间兼容通过。双端最新存档测试 `TurretPair06` 在客户端加载期间因资源压力中止，未形成通过结论。
